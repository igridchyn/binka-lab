## 3. Lanes, repos and isolation

| Lane | Repo and loop | Phases | `CHECK_CMD` adds |
|---|---|---|---|
| **binka** | `~/dev/binka`, this loop (`.autorun/`) | P0 docs; P1 exporter; the exporter deltas in P3 and P4; P6's talk tracks | `PYTHONPATH=. pipenv run pytest showcase/tests -q` (P1 §9; fixtures only, < 10 s) |
| **lab** | `~/dev/binka-lab`, its **own** loop, set up with `/autorun:init` at P2.0 | P2–P6 site work | `npm run check`: tsc, eslint, vitest, the content build, Playwright + axe |
| **operator** | — | every gate, every publication (g), testers, the voice-over, account setup | — |

**Isolation, the one-way rule (D5) extended to sessions.** A lab-lane session never reads `~/dev/binka`. Its only
input from binka is the bundle the binka-lane exporter writes into `~/dev/binka-lab/data/bundle/`.
- The bundle is written uncommitted. A lab item commits it after its own checks: `verify-bundle` plus the scanner.
- binka-lab's `settings.loop.json` denies `Read(~/dev/binka/**)` and `Bash(*~/dev/binka*)`, and its
  `guard_rules.py` blocks a path into binka.
- So a public-repo session can't copy private text. Anything the site needs from binka goes through the exporter,
  which runs the sanitizer and scanner.

**Which loop runs: one at a time, with cards between them.** Both repos run in backlog mode
(`.autorun/backlog.json`): an operator touchpoint opens a **card** and the loop works on whatever isn't behind it.
It writes PAUSE only when nothing is left. A backlog covers only its own repo, so a handover between the repos is
an **operator-owned task** in binka's backlog (`E9.LAB.*`). Its card says "run the binka-lab loop through …", and
binka's loop has nothing eligible behind it until the operator answers `done`. binka's backlog is ordered so that
every exporter task that writes into `~/dev/binka-lab/data/bundle/` finishes **before** a hand-over. So the two
loops never run on the bundle at the same time.

## 4. Boundaries and cards

POLICY (a)–(f) apply unchanged in both lanes. E9 adds one:

- **(g) publication and accounts.** The loop prepares an `act` or `checkpoint` card with the exact steps, and the
  operator does them:
  - creating or changing anything on GitHub (the repo, its visibility, settings and secrets), Cloudflare (Pages,
    Access, DNS, Web Analytics) or Search Console;
  - merging to binka-lab's `production` branch, or to igor-web's;
  - flipping the repo public, or removing an Access policy;
  - posting or uploading anywhere (LinkedIn, YouTube), and contacting anyone (testers);
  - **every release's disclosure read**, which the operator signs (P3 §11.3 row 3, scoped to the release).

  **Pushes:** the lab loop's supervisor pushes only to `autorun/loop` on binka-lab's remote (once P2.0's setup has
  made it), which deploys a preview behind Access. `main` and `production` are the operator's merges. A push to a
  public repo is publication, so the recommended launch pushes the scanned commits to a fresh public repo, binka-lab
  stays private as the lab loop's working repo, and the operator moves each release after its release read
  (disclosure policy §4.9; P3 §11.4).
- **Excerpt review is a blocking act card.** A transcript or code excerpt enters the bundle only after the
  operator reads it (P0 §5.3). Excerpts are batched per release train.
